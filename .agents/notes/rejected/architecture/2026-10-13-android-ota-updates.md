# Agent Note: Android 资源包热更新

Status: rejected

原因：资源包改为 GitHub Releases 分发；现行实现见 [GitHub Android 热更新](../../implemented/architecture/2026-10-14-github-android-ota.md)。

## Problem

Android APK 使用 Capacitor 8，从 `https://localhost` 加载 `dist` 中的本地资源。`usePwaUpdate` 在原生平台停用 Service Worker，因此线上 Web 发布不会更新已安装 APK 的界面和前端逻辑。手机浏览器与 PWA 已通过 Service Worker 提供更新提示。

本提案面向 Android APK，目标是更新界面、前端业务逻辑与静态资产，同时保留离线启动和本地聊天数据。方案尚未接入应用，也未创建云端资源。

## Proposal

### 组件与职责

- 客户端拟采用与 Capacitor 8 匹配的 `@capgo/capacitor-updater` 8.x，锁定通过真机验证的具体版本。使用手动更新模式，由应用决定检查、下载和启用时机，避免更新过程打断聊天。
- 现有 Cloudflare Pages Functions 增加只读更新检查接口，返回与当前原生版本兼容的资源包信息；复用已有 API 线路回退机制。
- Cloudflare R2 保存不可变资源包和发布清单，通过 HTTPS 自定义域名分发。包使用包含版本的独立路径，发布后不覆盖。
- 发布脚本负责构建、打包、签名、上传和切换渠道指针。上传能力只在受控发布环境中提供，移动客户端不能发布更新。

原生配置拟设置 `autoUpdate: false`、`autoDeletePrevious: false`；默认关闭插件的第三方统计地址（`statsUrl: ""`），更新事件仅发送至本项目受控接口。渠道选择在本地与自建检查接口中完成，不调用托管平台的渠道接口。资源包清理保留当前包、一个成功回退包和内置包，避免长期累积磁盘占用。

插件支持自托管和手动下载、启用资源包，无需使用 Capgo 托管服务。[官方手动更新文档](https://capgo.app/docs/plugins/updater/self-hosted/manual-update/)、[插件源码与版本迁移说明](https://github.com/Cap-go/capacitor-updater)。R2 正式分发使用自定义域名；`r2.dev` 适合开发测试。[R2 公共存储桶文档](https://developers.cloudflare.com/r2/buckets/public-buckets/)。

### 更新范围与版本兼容

| 内容 | 发布方式 |
| --- | --- |
| React 页面、CSS、前端逻辑、图片和本地文案 | 资源包热更新 |
| 服务端模型、提示词和 Functions 逻辑 | 服务端发布 |
| 原生插件、Android 权限、Gradle、Capacitor 原生依赖 | 新 APK |
| 安装热更新插件与内置验签公钥 | 首次发放带更新能力的新 APK |

版本同时记录原生 `versionCode`、资源包 `bundleVersion` 和原生能力标识 `runtimeVersion`。检查接口按原生能力标识及允许的原生版本范围筛选包，禁止将依赖新插件的资源包发送给旧壳。当前仓库的原生版本为 `0.1.12`，原生构建号为 `12`；接入版本的实际编号在实现时确定。

更新保持 `appId`、WebView 的 `https://localhost` 来源及 Dexie 数据库名称稳定，保留聊天、记忆和模型设置。数据库变更优先新增字段，须保证保留的回退版本可读取；无法兼容的迁移应与原生版本范围绑定，且发布前验证数据恢复路径。

### 客户端流程

1. 启动时立即展示当前可用的本地资源包，检查更新在后台执行；断网或检查超时不阻塞聊天。
2. 有兼容更新时下载完整资源包至独立目录，验签及完整性校验通过后才进入“待启用”。第一版采用全量包，后续根据包体积和下载耗时评估增量分发。
3. 下载完成后提示“新版本已准备好”，提供“立即更新”和“稍后”。设置中显示原生版本、资源包版本和“检查更新”。中日文案共同维护。
4. 正在生成回复、压缩上下文、保存数据或存在未发送草稿时，暂缓切换；切到后台也不触发强制重载。用户选择立即更新时，先完成必要保存，再调用插件启用接口。
5. 每次启动在入口尽早调用 `notifyAppReady()`，不等待访问码校验、网络接口或聊天加载。缺少启动确认时由原生插件执行加载失败回退。

插件的启动确认仅证明 JavaScript 已启动，不能发现确认之后的所有业务错误。因此还需记录资源包启用、加载失败及回退事件，并为可复现的严重业务故障提供撤回版本和恢复入口。[插件 API 与启动确认契约](https://capgo.app/docs/plugins/updater/api/)、[源码对启动确认边界的说明](https://github.com/Cap-go/capacitor-updater)。

### 安全与回退

- 启用插件 Encryption V2，验签公钥随 APK 内置，私钥只在发布环境保存；同时使用 HTTPS 和完整性校验。不能把接口同时返回的普通 SHA256 当成发布者身份认证。[官方加密与签名机制](https://capgo.app/docs/live-updates/encryption/)。
- 固定允许的应用标识、平台和下载域名；网络响应先验证结构、版本及大小限制。未验签、解压失败或空间不足时保留当前可用包。
- 保留内置包及至少一个已确认可用的资源包。加载失败回退依赖本地原生能力，不依赖故障页面再次访问服务器。
- 业务故障通过撤回发布清单阻止继续分发；已安装设备在下次联网检查时收到恢复包。必要时将已验证旧内容重新签发为更高资源包版本，保持发布序号递增。
- 原生 APK 更新采用相同应用标识和签名，避免把卸载重装作为常规恢复方式。

### 发布流程

`精准门禁 → 构建 dist → 官方 CLI 打包与签名 → 上传不可变包 → beta 真机验证 → 切换 stable 发布指针`

资源包上传完整并校验可下载后，再以单对象写入切换渠道清单。检查接口使用不缓存的发布元数据；版本化包可长期缓存。先用 beta 内测渠道和 stable 正式渠道，按需增加分批发布。第一版不建设完整发布管理后台。

### 接入顺序

1. 增加原生更新服务与应用级生命周期 hook，封装平台判断、启动确认、更新状态和订阅清理；Web 平台沿用现有 PWA 通道。
2. 增加 `POST /api/app-update` 检查接口。请求携带应用标识、平台、原生构建号、能力标识、当前资源包版本和渠道；响应明确区分无更新、可热更新和需升级 APK。
3. 增加设置中的版本信息及检查入口，复用现有更新提示样式；“待启用”状态需与流式回复、压缩、持久化和草稿状态联动。
4. 增加资源包构建、签名、上传、渠道发布和撤回脚本，完成 beta 真机验证后生成首个具备更新能力的 APK。

实施门禁覆盖前端单元测试、Functions 测试、三份类型检查、Lint 和 Web E2E；Android 另行验证真实下载、签名拒绝、离线启动、失败回退及升级前后 IndexedDB 数据一致性，不能以浏览器测试替代。

## Alternatives considered

- 将 Capacitor `server.url` 改为线上站点：每次启动依赖远端页面，改变现有离线资源与存储边界，也不具备资源包启用和回退机制；官方将其定位为开发时实时重载配置。[Capacitor 配置文档](https://capacitorjs.com/docs/config)。
- 为 APK 启用现有 PWA Service Worker：无法更新原生能力，并会与原生资源包缓存形成两套激活机制；浏览器/PWA 保留原有更新通道。
- 自行编写 Android 下载、解压、资源切换与回退插件：原生故障恢复成本较高，优先使用已有插件并验证其边界。
- 直接采用托管热更新平台：可减少发布系统工作，但本项目已有 Cloudflare 基础设施，优先评估自托管资源分发。

## Acceptance criteria

- 完成首次升级 APK 后，后续纯前端版本无需重新下载 APK 即可更新。
- 断网冷启动、更新下载中断、包被篡改、空间不足、启动 JavaScript 失败时仍有本地可用版本。
- 更新和回退均保留聊天、记忆、API Key 配置与访问状态，未发送草稿不会因自动切换丢失。
- 流式回复期间不启用新资源包；完成后可按用户选择安全切换。
- 不兼容原生版本无法接收该资源包；PWA 的更新流程独立工作。
- beta 发布、stable 发布、版本撤回和恢复均有可执行脚本，并在 Android 真机上验证。

## Risks

- 当前已安装 APK 没有更新插件，必须先安装一次具备更新能力的新 APK。
- 启动确认后的业务错误不会自动触发插件的加载失败回退，需要应用级恢复策略与发布监测。
- 资源包回退不会撤销数据库写入；不兼容的数据迁移会破坏恢复能力。
- R2、分发域名和发布密钥尚未配置；实际网络可达性、设备 WebView 兼容性和完整更新周期须在接入时验证。
